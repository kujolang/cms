# CMS 1.2.0

CMS 1.2.0 releases the work since v1.1.0: portable Ability contracts, request-bound approvals, two hardening passes, and faster scheduler and worker processing.

## Upgrade

Back up the database and managed media/extension storage before upgrading. Stop workers during the change, install the pinned dependencies with `kennel install`, then start `backend/runtime/main.kujo`. Startup applies database migrations, including schema 13 for Ability approvals.

- Ability mutations now require a short-lived approval for the exact invocation. `confirmed: true` grants no authority. Use `scripts/cms-ai.sh approve` and `run-approved`, or the matching API/client methods. Preserve the caller's principal and idempotency key.
- The six-operation CMS Ability pack and pinned Ability runtime remain independently versioned at 1.0.1. The CMS application version does not change Ability schema revisions.
- Sessions and approvals expire at their configured deadlines. Clients must handle expiry and obtain fresh authority.
- Public media reads consume the configured public rate limit. Tune ingress and CMS quotas for expected traffic.
- Extension replacement removes only managed package directories with a matching server-owned receipt. Legacy unmarked directories are preserved; inspect ownership before removing them manually.
- Atomic composition advances `updated_at` even for term-only edits. Clients should keep the returned timestamp for `expected_updated_at` on their next edit.
- Webhook destinations are revalidated and redirects do not bypass the destination policy. Keep allowlists explicit.
- Older installations crossing schema 9 must reissue legacy database-backed tokens. A configured bootstrap token remains available only when explicitly enabled.

REST route names, response envelopes, environment variable names, theme/plugin manifest revisions, and public read-only WebMCP contracts remain unchanged. The Kennel package includes JavaScript and PHP clients and the Ability pack. Kennel excludes all `.env.*` files by policy, including `.env.example`; use the [tagged environment reference](https://github.com/kujolang/cms/blob/v1.2.0/.env.example) when configuring a registry installation. Git clones include that template.

## Verification and measured effects

The two repository audits record regression checks and measurements:

- [First hardening pass](../audits/repository-hardening.md)
- [Second hardening pass](../audits/repository-hardening-round-2.md)

In the recorded local fixtures, a 500-entry scheduler batch used one SQLite process instead of 502 and took 0.067 seconds instead of 11.820 seconds. The median five-job worker run fell from 6.430 to 1.967 seconds across three samples. These measurements describe those fixtures, not production latency guarantees.

Run `CMS_GATE_PERF_RUNS=10 bash scripts/run-release-gate.sh` before deployment. The gate covers contracts, clients, startup, integrations, security, workers, recovery, and performance budgets. Each deployment still owns its identity adapter, trusted ingress, secrets, durable storage, backups, and monitoring.
